1. Overview

This system is a centralized Feature Management Service for an e-commerce platform serving more than 100 applications across web, backend, and mobile clients. The primary design goal is to keep flag evaluation latency below P99 5 ms while the number of flags, rules, segments, and client applications continues to grow.

The backbone of the design:

  • Control plane for flag authoring, approval, rollout, audit, and publishing
  • Data plane for ultra-fast local or edge evaluation
  • Five-level cache: SDK in-process → CDN → JVM → Redis → S3
  • Push-first distribution with immutable SHA-256-checksummed snapshots and delta sync
  • Explainability-first: every flag decision is reconstructable with standardized reason codes
  • Kubernetes multi-region deployment: active-active data plane, active-standby control plane

3. Design Principles

  • Evaluate close to the caller — P99 < 5 ms via in-process SDK evaluation, zero network calls
  • Push-first config distribution; polling as fallback only
  • Immutable, SHA-256-checksummed versioned snapshots — cache invalidation is version switching
  • Compile rules ahead of time; runtime is pure in-memory lookup
  • Standardized reason codes returned from the same evaluation model used for decisions
  • Scope payloads by environment + appScope — client memory proportional to what that app uses
  • Five-level cache hierarchy so each layer protects the next

4. Main Components

4.1 Control Plane

  • Flag management: create, archive, tag, group, assign ownership, set default values
  • Environment management: dev, staging, prod, region, tenant
  • Rollout management: percentage rollout (basis points), allowlists, segment rules, time windows
  • Release association: bind flags to release trains, experiments, incident kill switches
  • Audit and approval: track who changed what and when; enforce approval workflows for production

4.2 Rule Compiler

  • Validates schema and rule references
  • Resolves segment dependencies; detects prerequisite chains and mutex flag conflicts
  • Precompiles match trees and SHA-256-based rollout plans
  • Produces immutable snapshot bundles and delta events
  • Assigns monotonic version numbers per environment + appScope
  • Publishes version-change events to Kafka for fan-out distribution

4.3 Snapshot Store (L5)

  • Keyed by environment + appScope + version
  • Write-once, never mutated — version is the identity
  • Backed by S3-compatible object storage; served through CDN (L2)
  • Supports full snapshot fetch and delta fetch from a known version

4.4 Distribution Gateway

  • SSE, WebSocket, or gRPC streaming for long-lived SDK connections
  • Emits lightweight invalidation events: { scope, version, checksum }
  • SDK fetches delta or full snapshot only when version changes
  • Falls back to CDN pull or direct S3 fetch if streaming unavailable

4.5 Evaluation Plane

  • Local SDK evaluation (primary) — in-process, zero network, P99 < 5 ms
  • Remote Evaluation API (fallback) — for thin clients, server-side templates, emergency
  • Remote nodes load snapshots from Redis (L4), then S3 (L5) on miss

4.6 Explainability and Audit Store

  • Management audit log: always retained; append-only
  • Evaluation traces: sampled at 1% by default; debug-on-demand per flagKey / subjectKey / traceId
  • Stores normalized reason codes, rollout bucket, matched rule, snapshot version
  • Backed by Elasticsearch for queryability

4.7 Edge / Network Layer

  • WAF/Firewall: DDoS protection, IP allowlisting for SDK distribution endpoints
  • CDN: caches immutable snapshot versions by content address; hit rate target > 95%
  • Load Balancer: L4/L7 routing, health-based routing across K8S pods
  • API Gateway: authentication, rate limiting, routing to control vs. data plane

5. Five-Level Cache Hierarchy

5.1 Cache Levels

LevelLocationScopeInvalidationLatency
L1SDK in-process memoryper app processversion push event< 1 ms
L2CDN edge nodescope + version (immutable)content-addressed, never evicted< 5 ms
L3JVM / evaluation node shared cacheper evaluation nodeversion push event< 2 ms
L4Redis clusterper environment + appScopeversion change publish< 5 ms
L5S3 / object storageper scope + version (immutable)never invalidated< 100 ms

Because snapshots are immutable by version, L2 and L5 never need explicit invalidation. A new publish creates a new version object. Clients switch versions atomically after validating the checksum.

5.2 Scope-Based Packaging

  • Bundle by appScope: each app receives only its relevant flags
  • Separate bundles per environment (dev / staging / prod are always distinct)
  • Global flags (shared across apps) form a separate named scope
  • Client memory proportional to flags actually used, not the global catalog

5.3 Delta Sync Protocol

Client state maintained by SDK:

{ "scope": "prod:checkout-web", "version": 124,
  "checksum": "sha256:abc123...", "lastRefreshedAt": "..." }

On publish:

  1. Compiler publishes { scope, newVersion, checksum } to Kafka
  2. Streaming gateway fans out to all connected SDK instances for that scope
  3. SDK compares received version to local version
  4. If delta available and within retention window → fetch delta only
  5. If delta chain broken or checksum fails → fetch full snapshot from CDN (L2)
  6. SDK atomically replaces in-memory snapshot and updates local state

5.4 Cost Controls

  • Compress snapshot payloads (Brotli or gzip)
  • Precompiled rule structures — no DSL parsing at runtime
  • Deduplicate shared segments and targeting metadata across flags in the bundle
  • TTL only on fallback polling; primary freshness is event-driven
  • Redis keys at environment:appScope granularity, not per-user

5.5 Failure Behavior

  • SDK continues using last known good snapshot on network loss
  • Mobile SDKs persist last snapshot to local storage for offline startup
  • Every snapshot includes publishedAt, version, optional expiresAt
  • Flag categories declare failOpen or failClosed per flag
  • Remote evaluation nodes degrade to cached Redis snapshot if S3 unreachable

6. SDK Design

6.1 Goals

  • Same conceptual API across Java, Go, Node.js, iOS, Android, and Web
  • Local evaluation by default — zero network calls on hot path
  • Deterministic evaluation behavior across all languages
  • Offline-safe for mobile clients

6.2 Common SDK Interface

initialize(config): Promise<void>
boolVariation(flagKey, context, defaultValue): boolean
stringVariation(flagKey, context, defaultValue): string
numberVariation(flagKey, context, defaultValue): number
jsonVariation(flagKey, context, defaultValue): object
getEvaluationDetails(flagKey, context, defaultValue): EvaluationDetails
trackExposure(flagKey, context, result): void
flush(): Promise<void>
close(): void

Normalized context schema:

  • subjectKey: userId / deviceId / sessionId / merchantId
  • attributes: region, appVersion, platform, locale, membershipLevel, tenantId

6.3 SDK Runtime Model

  1. Bootstrap from local persisted snapshot if available (mobile offline start)
  2. Start background streaming connection (SSE or gRPC) for push updates
  3. Fall back to polling if streaming unavailable
  4. Evaluate flags against in-memory compiled snapshot — no network call
  5. Emit exposure events and health metrics asynchronously via batched queue
  6. On version push: fetch delta or full snapshot, validate checksum, atomically swap

6.4 Cross-Language Consistency

  • Shared evaluation specification document
  • SHA-256 hash algorithm: hash(flagKey + ":" + subjectKey) % 10000
  • Defined rule precedence: priority ascending, FIFO within equal priority
  • Defined null/empty attribute handling
  • Golden test vectors for every SDK — CI enforces no divergence

7. Evaluation Engine

7.1 Evaluation Steps

For each evaluate(flagKey, context) call:

  1. Load active snapshot from L1 (in-process SDK cache)
  2. Look up flagKey — if not found → return caller default with FLAG_NOT_FOUND
  3. If flag.enabled = false → return flag default with FLAG_DISABLED
  4. Iterate rules by priority (ascending):
    • If conditions do not match context → continue
    • Compute bucket: SHA-256(flagKey + ":" + subjectKey) % 10000
    • If bucket < rolloutBps → return variation with RULE_MATCH
    • If bucket ≥ rolloutBps → record ROLLOUT_NOT_INCLUDED, continue
  5. No rule matched or all rollout checks excluded → return flag default with DEFAULT_VALUE

7.2 Reason Codes

CodeMeaning
FLAG_NOT_FOUNDFlag key does not exist in snapshot
FLAG_DISABLEDFlag exists but global enabled = false
RULE_MATCHA targeting rule matched and rollout bucket passed
ROLLOUT_NOT_INCLUDEDRule matched but subject fell outside rollout percentage
DEFAULT_VALUENo rule matched; flag default value returned
PREREQUISITE_FAILEDA required prerequisite flag was not satisfied
STALE_SNAPSHOT_FALLBACKEvaluation used an expired snapshot due to network failure

7.3 Percentage Rollout — SHA-256

bucket = SHA-256(flagKey + ":" + subjectKey) % 10000
enabled = bucket < rolloutBps  // rolloutBps: 0–10000, 5000 = 50%
  • 10,000 modulus → 0.01% granularity
  • SHA-256 guarantees uniform distribution across all languages
  • Same subject + flag always gets the same bucket (stable rollout)

11.3 Disaster Recovery

  • Data plane RTO: < 30 s — SDK uses stale snapshot automatically on disconnect
  • Control plane RTO: < 5 min — promote standby
  • RPO: zero after publish — S3 CRR replicates before acknowledgment
  • Mobile resilience: last snapshot persisted to local storage; no network required to evaluate

11.4 Emergency Kill Switch

  • Dedicated fast-publish lane bypassing normal approval workflow
  • Marked priority: critical — streaming gateway fans out within 3 seconds
  • SDK processes critical events ahead of normal version events

  • RBAC by team, environment, and app scope
  • Approval workflow for production publishes; fast-path for kill switches
  • Immutable audit log for every management mutation
  • Rotating signed SDK credentials per app scope

  • WAF rules blocking abnormal snapshot polling burst patterns

16. Interview Summary

Key tradeoffs to emphasize:

  1. Control / data plane separation — different SLOs, scale behaviors, consistency requirements
  2. Local evaluation first — P99 < 5 ms because evaluation is in-process against an in-memory snapshot
  3. Immutable versioned snapshots — cache invalidation is version switching; CDN cache never expires
  4. Five-level cache hierarchy — each layer protects the next; CDN makes snapshot distribution nearly free at scale
  5. Scope-based packaging — client payload size proportional to what that app uses, not the global catalog
  6. SHA-256 rollout at 0.01% granularity — consistent across all SDK languages, stable per user
  7. Explainability in the evaluation contract — reason codes, rollout bucket, matched rule all built-in
I split the system into a control plane for authoring and publishing, and a data plane for high-performance evaluation. Configuration changes compile into immutable SHA-256-checksummed snapshots scoped per application. A five-level cache hierarchy — SDK in-process → CDN → JVM → Redis → S3 — ensures most evaluations never leave the process. Kafka-driven streaming notifies SDKs within seconds, SDKs fetch only the delta. P99 < 5 ms, data plane scales independently, every decision is fully reconstructable.
