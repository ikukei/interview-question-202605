1. 文档目的

本文档描述面向电商平台的功能开关管理服务的实际设计方案。系统需要管理跨 Web 门户、后端服务和移动客户端的功能开关，支持低延迟评估（进程内 P99 < 5 ms）、精细化灰度发布、清晰的归属关系和可解释的决策过程。

由于这是一道 take-home 面试项目，设计有意区分以下三个层次：

  • 生产级系统应当支持的能力
  • Demo 实现应该构建的内容
  • 在 Demo 中只需文档说明、无需实现的部分
Demo 的目标不是重建 LaunchDarkly，而是展示扎实的工程判断力：清晰的架构、实用的 API、确定性的评估行为、合理的缓存设计、测试覆盖，以及从 Demo 到生产的演进路径。

2. 需求概览

  • 100+ 应用和服务中的千级功能开关
  • Web、后端和移动客户端全端覆盖
  • 高吞吐、低延迟评估 — 进程内 P99 < 5 ms
  • 随目录增长保持低分发成本的五层缓存体系
  • 跨多语言易于集成的客户端 SDK 模型
  • 管理、分发、评估和解释 API
  • 可观测性和调试支持
  • 每次决策均可解释：哪个 subject、哪个区域、哪条规则、哪个灰度分桶、哪个快照版本

3. 设计哲学

最重要的设计决策是将系统拆分为两个平面。

控制面负责编辑、校验、发布、审计和治理，可以容忍更高延迟和更强一致性要求。

数据面负责开关评估，需要快速、高可用、缓存友好，并在正常运行时与控制面解耦。

贯穿 Demo 和生产的核心设计决策：

  • 不可变、版本化、SHA-256 校验的快照作为运行时单元，而非单条开关记录
  • 按 environment + appKey 划分快照包
  • SHA-256 灰度哈希分桶，模数 10,000，精度 0.01%
  • 每次评估响应均包含标准化原因码
  • 可解释性是评估协议的组成部分，而非事后补日志

9. 快照与缓存设计

9.1 快照结构

{
  "appKey": "checkout-service",
  "environment": "prod",
  "version": 42,
  "checksum": "sha256:abc123ef...",
  "publishedAt": "2026-05-21T08:00:00Z",
  "flags": [
    {
      "flagKey": "new-checkout",
      "type": "boolean",
      "enabled": true,
      "defaultValue": false,
      "releaseKey": "release-2026-05-checkout",
      "rules": [
        {
          "ruleId": "rule-1", "priority": 1,
          "conditions": [
            { "attribute": "region", "operator": "equals", "value": "cn-east" }
          ],
          "rolloutBps": 5000,
          "variationValue": true
        }
      ]
    }
  ]
}
rolloutBps 以 basis points（0–10000）存储灰度比例，精度 0.01%。checksum 是规范化 JSON 的 SHA-256。快照写一次，发布后永不修改。

9.2 五层缓存（Demo vs 生产）

层级位置Demo生产
L1SDK 进程内内存不适用（SDK 直接调用 API）SDK 持有编译后快照
L2CDN 边缘未实现CDN 按 version 内容寻址，永不过期
L3JVM / 服务进程内ConcurrentHashMap，后端持有每个评估节点进程内缓存
L4Redis 集群未实现跨进程共享，按 scope 划分最新快照
L5持久化存储H2 ff_config_snapshot 表S3 兼容对象存储

Demo 缓存 key：environment + ":" + appKey。发布时更新 L3；评估 miss 时从 H2（L5）加载并预热 L3。

10. 评估引擎

10.1 评估算法

evaluate(snapshot, flagKey, context, callerDefault):

1. 按 flagKey 在快照中查找开关
   → 未找到: { value: callerDefault, reasonCode: FLAG_NOT_FOUND }

2. flag.enabled == false:
   → { value: flag.defaultValue, reasonCode: FLAG_DISABLED }

3. 按 priority 升序遍历规则:
   a. 对 context.attributes 评估 rule.conditions
      → 不匹配: 继续下一条
   b. bucket = SHA-256(flagKey + ":" + context.subjectKey) % 10000
   c. bucket < rule.rolloutBps:
      → { value: rule.variationValue, reasonCode: RULE_MATCH,
          matchedRuleId: rule.ruleId }
   d. bucket >= rule.rolloutBps:
      → 记录 ROLLOUT_NOT_INCLUDED，继续

4. 无规则命中 / 全部排除:
   → { value: flag.defaultValue, reasonCode: DEFAULT_VALUE }

10.2 原因码

原因码含义
FLAG_NOT_FOUND快照中不存在该 flagKey
FLAG_DISABLED开关存在但 enabled = false，返回开关默认值
RULE_MATCH规则命中且 subject 通过灰度，返回变体值
ROLLOUT_NOT_INCLUDED规则条件命中但 subject 分桶被排除
DEFAULT_VALUE无规则命中，返回开关默认值
PREREQUISITE_FAILED前置开关条件未满足
STALE_SNAPSHOT_FALLBACK无新鲜快照可用，使用最后已知快照

10.3 灰度分桶 — SHA-256

// Java — 跨语言兼容实现
String seed = flagKey + ":" + subjectKey;
byte[] hash = MessageDigest.getInstance("SHA-256")
                           .digest(seed.getBytes(UTF_8));
long bucket = (Longs.fromByteArray(Arrays.copyOf(hash, 8))
               & Long.MAX_VALUE) % 10000;
boolean included = bucket < rolloutBps;
  • SHA-256：无语言特定的溢出或字节序问题
  • 模数 10,000：最小粒度 0.01%
  • Java、Go、Python、Swift、Kotlin、TypeScript 结果完全一致
  • CI 通过黄金测试向量强制保证一致性

10.4 条件操作符

操作符说明
equals精确字符串匹配
not_equals否定字符串匹配
contains子字符串匹配
in / not_in值在集合内 / 不在集合内
semver_gte / semver_lt语义版本比较
regex正则表达式匹配

11. 可解释性设计

可解释性是评估协议的组成部分，而非事后附加。

POST /api/v1/evaluations:explain

{
  "flagKey": "new-checkout", "finalValue": true,
  "reasonCode": "RULE_MATCH",
  "appKey": "checkout-service", "environment": "prod",
  "subjectKeyHash": "sha256:d4e5f6...",
  "matchedRuleId": "rule-1",
  "matchedConditions": ["region equals cn-east"],
  "evaluatedRuleCount": 2,
  "rolloutBucket": 3721, "rolloutBps": 5000,
  "releaseKey": "release-2026-05-checkout",
  "snapshotVersion": 42,
  "evaluatedAt": "2026-05-21T08:00:01Z"
}
subjectKey 不以原始形式记录，始终在存储前进行 SHA-256 哈希。

生产追踪策略：默认 1% 采样；支持按 flagKey、subjectKey 或 traceId 按需开启全量追踪，无需重新部署。

小而精，推荐页面：

14. Java SDK 示例

FeatureClient client = FeatureClient.builder()
    .baseUrl("http://localhost:8080")
    .appKey("checkout-service")
    .environment("local")
    .build();

// 布尔评估
boolean enabled = client.boolVariation(
    "new-checkout",
    FeatureContext.builder()
        .subjectKey("user-123")
        .attribute("region", "cn-east")
        .attribute("platform", "ios")
        .build(),
    false  // 调用方默认值
);

// 获取完整决策详情
EvaluationDetails details = client.getEvaluationDetails(
    "new-checkout",
    FeatureContext.builder().subjectKey("user-123").build(),
    false
);
// details.getReasonCode()      → ReasonCode.RULE_MATCH
// details.getMatchedRuleId()   → "rule-1"
// details.getRolloutBucket()   → 3721
// details.getSnapshotVersion() → 42

生产 SDK 需额外实现（Demo 文档说明，不实现）：

  • 启动时从流式网关加载快照到 L1 缓存
  • 后台 SSE 或 gRPC 连接接收推送更新
  • 流式断连时自动切换轮询
  • 从最后一次持久化快照离线兜底
  • 曝光事件批量异步上报
  • 黄金测试向量跨语言一致性验证

21. 最终建议

  • Explain API 作为评估协议的组成部分
