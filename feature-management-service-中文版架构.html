1. 概述

本系统是一个面向电商平台的集中式功能开关管理服务，服务于 100+ 应用，覆盖 Web、后端服务和移动客户端。核心设计目标是：在功能开关数量、规则复杂度、客户端数量持续增长的情况下，将开关评估延迟控制在 P99 < 5 ms。

系统骨架由以下部分构成：

  • 控制面：开关编辑、审批、灰度发布、审计和发布管理
  • 数据面：极低延迟的本地或边缘评估
  • 五层缓存：SDK 进程内 → CDN → JVM → Redis → S3
  • 推送优先的配置分发：不可变快照 + SHA-256 校验 + 增量同步
  • 可解释性优先：每次开关决策均可追溯，内置标准化原因码
  • Kubernetes 多区域部署：数据面 active-active，控制面 active-standby

3. 设计原则

  • 尽量靠近调用方评估 — SDK 进程内评估，P99 < 5 ms，不走网络
  • 配置分发推送优先，轮询作为兜底
  • 不可变的、SHA-256 校验的版本化快照 — 缓存失效等同于版本切换
  • 规则提前编译 — 运行时只做纯内存查找，无 DSL 解析
  • 标准化原因码从同一评估模型中返回，而非事后补日志
  • 按 environment + appScope 划分快照包 — 客户端内存不随全局开关总数线性增长
  • 五层缓存，每层保护下一层

4. 核心组件

4.1 控制面

  • 开关管理：创建、归档、打标签、分组、指定负责人、设置默认值
  • 环境管理：dev / staging / prod / region / tenant
  • 灰度管理：百分比灰度（basis points 精度）、白名单、分群规则、时间窗口
  • 发布关联：绑定到发布火车、实验和故障 kill switch
  • 审计与审批：记录谁在什么时候做了什么；生产环境强制审批流程

4.2 规则编译器

  • 校验 schema 和规则引用
  • 解析分群依赖关系；检测前置条件链和互斥开关冲突
  • 预编译匹配树和 SHA-256 灰度分桶计划
  • 生成不可变快照包和增量事件
  • 按 environment + appScope 分配单调递增的版本号
  • 向 Kafka 发布版本变更事件，触发扇形分发

4.3 快照存储（L5）

  • 按 environment + appScope + version 寻址
  • 写一次，永不修改 — 版本号即身份
  • 由 S3 兼容对象存储承载；通过 CDN（L2）对外服务
  • 支持全量快照拉取和从已知版本的增量拉取

4.4 流式分发网关

  • SSE、WebSocket 或 gRPC 流式长连接
  • 推送轻量版本变更事件：{ scope, version, checksum }
  • SDK 仅在版本变化时拉取增量或全量快照
  • 流式连接不可用时，退回 CDN 拉取或直接从 S3 获取

4.5 评估层

  • 本地 SDK 评估（主路径） — 进程内，零网络调用，P99 < 5 ms
  • 远程评估 API（辅助路径） — 面向轻量客户端、服务端模板渲染、紧急兜底
  • 远程评估节点优先从 Redis（L4）加载快照，miss 时回退到 S3（L5）

4.6 可解释性与审计存储

  • 管理操作审计日志：永久保留，追加写入
  • 评估决策追踪：默认 1% 采样；支持按 flagKey / subjectKey / traceId 按需开启全量追踪
  • 存储标准化原因码、灰度分桶值、命中规则、快照版本
  • 由 Elasticsearch 承载，支持查询

4.7 边缘与网络层

  • WAF / 防火墙：DDoS 防护、SDK 分发端点 IP 白名单
  • CDN：按内容寻址缓存不可变快照版本；命中率目标 > 95%
  • 负载均衡：L4/L7 路由，基于健康状态在 K8S Pod 间分发
  • API 网关：鉴权、限流、路由到控制面或数据面

5. 五层缓存体系

5.1 缓存分层

层级位置作用域失效方式延迟
L1SDK 进程内内存每个应用进程版本推送事件< 1 ms
L2CDN 边缘节点scope + version（不可变）内容寻址，永不失效< 5 ms
L3JVM / 评估节点共享内存每个评估节点版本推送事件< 2 ms
L4Redis 集群每个 environment + appScope版本变更发布< 5 ms
L5S3 / 对象存储每个 scope + version（不可变）永不失效< 100 ms

因为快照按版本不可变，L2 和 L5 永远不需要主动失效。新发布创建新版本对象，客户端在校验 checksum 后原子切换到新版本。

5.2 基于 AppScope 的分包

  • 按 appScope 分包：每个应用只收到它用到的开关
  • 按 environment 严格隔离（dev / staging / prod 永远是独立快照）
  • 全局共享开关（多 app 共用）作为独立命名 scope
  • 客户端内存消耗与实际使用量成正比，不随全局目录增长

5.3 增量同步协议

SDK 维护的本地状态：

{ "scope": "prod:checkout-web", "version": 124,
  "checksum": "sha256:abc123...", "lastRefreshedAt": "..." }

发布时：

  1. 规则编译器向 Kafka 发布 { scope, newVersion, checksum }
  2. 流式网关扇形推送到该 scope 下所有已连接 SDK
  3. SDK 对比本地版本和收到的版本
  4. 如增量在保留窗口内且可用 → 仅拉取增量
  5. 如增量链路中断或 checksum 校验失败 → 从 CDN（L2）拉取全量快照
  6. SDK 原子替换进程内快照并更新本地状态

5.4 成本控制

  • 快照 payload 压缩（Brotli 或 gzip）
  • 预编译规则结构，运行时无 DSL 解析
  • 在 bundle 中对共享分群和通用目标元数据去重
  • TTL 只作用于兜底轮询；主要新鲜度由事件驱动
  • Redis key 按 environment:appScope 粒度，不按用户粒度

5.5 故障降级

  • 网络断开时 SDK 继续使用最后一次已知的好快照
  • 移动端 SDK 将快照持久化到本地存储，支持离线启动
  • 每个快照包含 publishedAt、version 和可选的 expiresAt
  • 每个 flag 类别可配置 failOpen（开放）或 failClosed（关闭）降级策略
  • 远程评估节点在 S3 不可达时降级到 Redis 缓存快照

6. SDK 设计

6.1 设计目标

  • Java、Go、Node.js、iOS、Android、Web 具有相同的概念 API
  • 默认本地评估 — 热路径不走网络
  • 所有语言评估行为确定性一致
  • 移动端支持离线模式

6.2 统一 SDK 接口

initialize(config): Promise<void>
boolVariation(flagKey, context, defaultValue): boolean
stringVariation(flagKey, context, defaultValue): string
numberVariation(flagKey, context, defaultValue): number
jsonVariation(flagKey, context, defaultValue): object
getEvaluationDetails(flagKey, context, defaultValue): EvaluationDetails
trackExposure(flagKey, context, result): void
flush(): Promise<void>
close(): void

标准化 context 结构：

  • subjectKey：userId / deviceId / sessionId / merchantId
  • attributes：region、appVersion、platform、locale、membershipLevel、tenantId

6.3 SDK 运行时模型

  1. 从本地持久化快照启动（移动端离线启动）
  2. 建立后台流式连接（SSE 或 gRPC）接收推送更新
  3. 流式连接不可用时退回轮询
  4. 对进程内编译快照进行评估 — 不走网络
  5. 通过批量队列异步上报曝光事件和健康指标
  6. 收到版本推送时：拉取增量或全量快照，校验 checksum，原子替换

6.4 跨语言一致性

  • 统一评估规范文档
  • SHA-256 哈希算法：hash(flagKey + ":" + subjectKey) % 10000
  • 统一规则优先级：priority 升序，相同 priority FIFO
  • 统一 null/empty 属性处理语义
  • 黄金测试向量（golden test vectors）：每个 SDK 均运行同一套输入 → 期望输出，CI 强制不能偏离

7. 评估引擎

7.1 评估步骤

每次 evaluate(flagKey, context) 调用：

  1. 从 L1（SDK 进程内缓存）加载活跃快照
  2. 按 flagKey 查找开关 — 未找到则返回调用方默认值，原因码 FLAG_NOT_FOUND
  3. 若 flag.enabled = false → 返回开关默认值，原因码 FLAG_DISABLED
  4. 按 priority 升序遍历规则：
    • 条件不匹配 context 属性 → 继续下一条
    • 计算分桶：SHA-256(flagKey + ":" + subjectKey) % 10000
    • 若 bucket < rolloutBps → 返回规则变体，原因码 RULE_MATCH
    • 若 bucket ≥ rolloutBps → 记录 ROLLOUT_NOT_INCLUDED，继续
  5. 无规则命中或所有灰度校验均排除该 subject → 返回开关默认值，原因码 DEFAULT_VALUE

7.2 决策原因码

原因码含义
FLAG_NOT_FOUND快照中不存在该 flagKey
FLAG_DISABLED开关存在但 enabled = false
RULE_MATCH目标规则命中且灰度分桶通过
ROLLOUT_NOT_INCLUDED规则条件命中但 subject 被灰度排除
DEFAULT_VALUE无规则命中，返回开关默认值
PREREQUISITE_FAILED前置开关条件未满足
STALE_SNAPSHOT_FALLBACK网络故障，使用过期快照评估

7.3 灰度分桶 — SHA-256

bucket = SHA-256(flagKey + ":" + subjectKey) % 10000
enabled = bucket < rolloutBps  // rolloutBps: 0–10000，5000 = 50%
  • 模数 10,000 → 最小粒度 0.01%
  • SHA-256 保证所有语言分布均匀，无整数溢出问题
  • 同一 subject + flag 永远得到相同 bucket（稳定灰度）

11.2 多区域策略

组件策略说明
控制面Active-Standby单主写入区域；主故障时 Standby 晋升
PostgreSQL主库 + 只读副本写主库，各区域读副本
S3 快照存储跨区域复制（CRR）所有区域均可访问快照
CDN全球 PoP按 version 内容寻址，边缘命中
数据面Active-Active每个区域独立服务本区域流量
Redis 集群每区域独立从 S3 独立加载，无跨区域依赖
流式网关每区域独立SDK 优先连本地区域网关

11.3 灾难恢复

  • 数据面 RTO：< 30 秒 — SDK 自动使用旧快照，无中断
  • 控制面 RTO：< 5 分钟 — Standby 晋升
  • RPO：发布后零数据丢失 — S3 CRR 在确认前完成复制
  • 移动端韧性：最后一次快照持久化到本地存储，无网络可评估

11.4 紧急 Kill Switch

  • 专用快速发布通道，绕过常规审批流程
  • 标记为 priority: critical — 流式网关 3 秒内扇形推送到所有 SDK
  • SDK 优先处理 critical 事件，排在普通版本事件之前

14. 安全与治理

  • 按团队、环境、应用 scope 进行 RBAC 权限控制
  • 生产环境发布强制审批流程；kill switch 设有快速通道
  • 所有管理操作的不可变审计日志
  • 按 appScope 轮换签名 SDK 凭证
  • 传输层 TLS 1.3；静态存储 AES-256
  • subjectKey 在记录前始终 SHA-256 哈希 — 原始 ID 不入日志
  • WAF 规则阻断异常快照轮询突发流量

16. 架构总结

关键 Trade-off：

  1. 控制面 / 数据面分离 — 不同 SLO、伸缩方式、一致性要求
  2. 本地评估优先 — P99 < 5 ms，进程内读内存，不走网络
  3. 不可变版本化快照 — 缓存失效等同于版本切换；CDN 缓存永不过期
  4. 五层缓存体系 — 每层保护下一层；CDN 让大规模快照分发几乎零成本
  5. 基于 AppScope 的分包 — 客户端 payload 与实际用量成正比
  6. SHA-256 分桶，0.01% 精度 — 所有 SDK 语言一致，用户稳定
  7. 可解释性内建于评估协议 — 原因码、灰度分桶、命中规则全部内置
系统被拆分为负责编写和发布的控制面，以及负责高性能评估的数据面。配置变更被编译成 SHA-256 校验的不可变快照并按 appScope 分包，五层缓存（SDK 进程内 → CDN → JVM → Redis → S3）确保绝大多数评估不离开进程。Kafka 驱动的流式推送在秒级内通知 SDK，SDK 只拉取增量。P99 < 5 ms，数据面独立扩展，每次决策完整可追溯。
